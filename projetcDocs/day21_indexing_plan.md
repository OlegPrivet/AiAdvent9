# День 21 — подключаемый RAG для `agi`

## Что должно работать

Пользователь сам выбирает документы из **любого доступного ему пути**, добавляет их через CLI и затем задаёт обычный
вопрос в `agi`. Приложение ищет подходящие фрагменты в локальном индексе, передаёт их главному агенту как справочные
данные и показывает, откуда взята информация. Корпус не зашит в программу и не ограничен файлами репозитория. Индекс
переживает перезапуск; документы можно добавлять, обновлять и удалять без пересборки остальных источников.

Пример конечного сценария:

```bash
export NEURALDEEP_API_KEY="<ключ>"
agi rag add ~/Documents/manual.pdf ~/Notes ./my-project/src
agi rag list
agi rag search "как устроено хранение чатов?"
agi
# в чате: /rag on
# затем обычный вопрос: Как устроено хранение чатов? Укажи источник.
```

Те же действия доступны внутри REPL и TUI: `/rag add <путь>`, `/rag list`, `/rag remove <id>`, `/rag refresh`,
`/rag search <запрос>`, `/rag compare ...`, `/rag on`, `/rag off`, `/rag status`, `/rag strategy fixed|structure`. Для
пути с пробелами `/rag add` берёт весь остаток строки после `add` как один путь; несколько путей за один вызов
передаются через shell-команду `agi rag add PATH...`. В TUI долгую индексацию выполнять в фоновом worker с прогрессом и
возможностью отмены, не блокируя отрисовку.

## Загрузка и локальный индекс

1. **Команды и состояние.** Расширить `src/cli.rs` подкомандой `agi rag`: `add PATH... [--dry-run]`, `list`, `status`,
   `remove ID`, `refresh`, `search QUERY [--strategy fixed|structure] [--limit N]`,
   `compare [--queries FILE] [--eval FILE] [--report FILE]`. В `src/main.rs` запускать эти команды до инициализации
   чата/TUI; ключ API нужен для реальной загрузки, обновления и поиска, но не для `list`, `status`, `remove` и
   `--dry-run`. Каталог, переданный в `add`, обходить рекурсивно; символические ссылки и служебные каталоги `.git`,
   `target`, `node_modules`, `.venv` пропускать. Отдельно указанный файл с таким именем всё равно разрешён. `--dry-run`
   показывает найденные документы, объём извлекаемого текста и оценку числа чанков без API-вызовов и записи; для
   изображений показывает число файлов, поскольку объём текста до OCR неизвестен. Добавление существующего пути
   обновляет его; `refresh` переиндексирует только изменившиеся зарегистрированные файлы, а для исчезнувших выводит
   ошибку и сохраняет старый индекс до явного `remove`.
2. **Форматы.** Принимать Markdown, обычный UTF-8 текст, исходный код независимо от расширения, HTML, DOCX, PDF,
   PNG/JPEG/WEBP/BMP/TIFF. Для PDF сначала извлекать текстовый слой с номерами страниц, для страниц без текста и для
   изображений использовать асинхронный NeuralDeep OCR (`/v1/ocr/*`, профиль `fast`, опрос не чаще раза в секунду); для
   DOCX извлекать абзацы и заголовки, для HTML — видимый текст и заголовки, для остальных файлов пробовать UTF-8 и
   отвергать бинарные данные. Если текст получить не удалось, явно сообщать об этом файле и не записывать пустой
   источник. При пакетной загрузке выводить результат по каждому файлу и итог, не теряя успешно обработанные файлы из-за
   одного ошибочного.
3. **Разбиение.** Для каждого документа строить **оба** набора чанков. `fixed`: 1200 Unicode-символов, перекрытие 200,
   границу сдвигать к слову. `structure`: не пересекать границы файлов и найденных разделов — Markdown/HTML/DOCX
   заголовки, страницы PDF, для кода верхнеуровневые объявления там, где их можно надёжно распознать, иначе логические
   блоки по пустым строкам; длинный раздел делить по абзацам/строкам до 1200 символов с перекрытием до 200 внутри
   раздела. Оба алгоритма сохраняют весь непустой текст и гарантируют продвижение на длинном слове. Для каждого чанка
   сохранять `source` (исходный путь), `title`/имя файла, `section` или страницу, `chunk_id`, стратегию, порядковый
   номер и текст. `chunk_id` стабилен для неизменённой версии файла и стратегии.
4. **Эмбеддинги.** По умолчанию использовать описанный в `projetcDocs/llm_docs.md` `POST /v1/embeddings`, модель `bge-m3`, пакет до
   16 текстов, ключ из `NEURALDEEP_API_KEY`. Дополнительно дать пользователю команды `agi rag embeddings set --url URL --model NAME [--api-key-env NAME]` и `/rag embeddings set URL NAME [KEY_ENV]` внутри REPL/TUI для собственного OpenAI-совместимого endpoint; при настройке проверять ответ сервиса и определять размерность. Проверять `data[].index`, полноту пакета, ожидаемую размерность,
   конечность чисел и ненулевую норму; нормировать векторы для косинусного поиска. Ограниченно повторять `429`/`5xx` с
   учётом `Retry-After`; ошибки авторизации и повреждённый ответ показывать пользователю без вывода ключа или
   заголовков. При `add` текст выбранных документов отправляется сервису эмбеддингов, а изображения и сканы — сервису
   OCR; явно написать это в справке команды. Секреты не сохранять, только имя переменной окружения.
5. **Хранилище.** В общем каталоге состояния `agi` (`XDG_STATE_HOME/agi` либо существующий платформенный путь) создать
   отдельную `rag.sqlite3`, не меняя схему `chats.sqlite3` ради векторов. Таблица источников хранит ID,
   исходный/канонический путь, формат, заголовок, контрольную сумму, число слов и время индексации; таблица чанков — ID
   источника, стратегию, метаданные, текст, модель и нормированный вектор как BLOB из 1024 `f32`. Уникальный ключ по
   `(source_id, strategy, chunk_id)`, индекс по источнику и стратегии. Сначала извлечь текст и получить все эмбеддинги
   для одного файла, затем одной транзакцией заменить **обе** его стратегии; при сбое старые чанки этого файла остаются
   доступны. Удаление источника удаляет его чанки, не затрагивая остальные. Изменение модели в будущем требует явной
   переиндексации, смешивать размерности нельзя. Сохранять активную конфигурацию эмбеддингов в SQLite и метку профиля у каждого чанка; после смены модели или URL блокировать поиск по старому индексу до `agi rag reindex`.

## Подключение к ответам `agi`

6. **Включение в чат.** В настройки чата добавить сохраняемые `rag_enabled` (по умолчанию `false`) и `rag_strategy` (по
   умолчанию `structure`). `/rag on|off` и `/rag strategy ...` меняют только текущий чат; shell-команда `agi rag add`
   пополняет общую библиотеку и не меняет другие чаты. `/rag status` показывает активность, стратегию, число
   источников/чанков и суммарное число слов. Такой явный переключатель сохраняет привычное поведение существующих чатов.
7. **Поиск перед ответом.** Когда RAG включён, перед обычным ответом и шагом задачи в REPL и TUI векторизовать вопрос
   той же моделью, выполнить косинусный поиск по активной стратегии и выбрать до четырёх чанков из разных частей корпуса
   в пределах 6000 символов. В `AgentRequest` передавать найденные фрагменты отдельно от текста пользователя и истории
   чата. В `main_messages` добавить их непосредственно перед вопросом как пронумерованные **недоверенные данные** с
   путём, разделом/страницей и `chunk_id`; потребовать ссылки `[1]`, `[2]` на использованные фрагменты и признание
   отсутствия ответа в документах. Сохранять в ответе видимый список найденных источников, чтобы ссылки не терялись
   после восстановления чата. Не записывать сырые фрагменты в память/историю как реплики пользователя. Если RAG включён,
   но индекс пуст или поиск упал, сообщить причину и команду исправления; не выдавать ответ без источников за ответ по
   документам.
8. **Единое поведение интерфейсов.** Реализовать операции `rag` в общем сервисе, вызываемом shell CLI, REPL и TUI.
   Добавить `/rag` в справку и палитру команд TUI. В TUI поиск/индексацию делать вне UI-потока; отменённый запрос не
   должен позже заменить текущий ответ. `agi rag search` и `/rag search` показывают score, `source`, `title`, `section`,
   `chunk_id` и короткий фрагмент; это позволяет проверить индекс до вопроса модели.

## Сравнение стратегий и сдача задания

9. **Сравнение на документах пользователя.** `agi rag compare` всегда выводит для обеих стратегий число чанков,
   среднюю/медианную/95-й перцентиль длины, долю коротких чанков и объём повторённого текста. С `--queries` показывает
   рядом top-3 результатов на одинаковых вопросах. С `--eval` (JSON: вопрос + путь источника и короткий точный эталонный
   фрагмент) дополнительно считает `hit@3` и `MRR@3`; без эталонов не выдаёт субъективную релевантность за числовую
   метрику. Отчёт по умолчанию печатается в терминал, `--report PATH` сохраняет Markdown.
10. **Воспроизводимый пример для Дня 21.** В README привести команду добавления `README.md` и шести исходных документов
    `projetcDocs/{invariants_testing,llm_docs,memory_layers,memory_testing,task_state_testing,task_transitions_testing}.md`,
    затем `agi rag status`,
    `agi rag compare --eval projetcDocs/day21_rag_eval.json --report projetcDocs/day21_chunking_comparison.md`,
    `/rag on` и пример вопроса. Эти семь файлов уже содержат около 14 тыс. слов, достаточно для минимального объёма;
    пользователь может добавить материалы из `projetcDocs/rag/` и любые собственные документы. Создать 8–10 эталонных
    вопросов по этим файлам, выполнить реальную индексацию при доступном ключе и записать фактические цифры и 2–3
    наблюдения о различиях стратегий. Индекс в пользовательском каталоге состояния не коммитить. Результат задания —
    работающие команды загрузки и RAG в чате, локальная БД с эмбеддингами/метаданными и отчёт сравнения.

## Проверки готовности

- Модульные тесты извлечения и chunking: несколько форматов, PDF с текстом и скан через mock OCR, UTF-8/кириллица,
  заголовок внутри code fence, длинный абзац, границы, полное покрытие и стабильность ID.
- HTTP-тесты с локальным mock-сервером: успешный пакет, переставленные индексы, неполный/дублированный ответ, неверная
  размерность, `401`, `429` и `5xx`; реальный API и ключ в тестах не нужны.
- Тесты БД и команд: добавление произвольного пути и каталога, повторное добавление, `refresh`, удаление, перезапуск,
  сохранение старого индекса при ошибке, обе стратегии и обязательные метаданные. Интеграционные тесты REPL/TUI
  проверяют `/rag on`, поиск до запроса модели, видимые ссылки и отсутствие RAG при `/rag off`; старые команды и чат
  работают как прежде.
- Перед сдачей выполнить `cargo fmt --all -- --check`, `cargo clippy --all-targets --all-features -- -D warnings`,
  `cargo test`, затем реальный прогон загрузки/сравнения с ключом. Проверить SQLite: каждый чанк имеет текст, `source`,
  `title`, `section`, `chunk_id` и 1024-мерный вектор; индекс после перезапуска доступен.
